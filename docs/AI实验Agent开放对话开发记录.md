# AlgoVerse AI 实验 Agent 开放对话开发记录

## 用户原始 Prompt

```text
请继续完善 AlgoVerse 智算万象现有的 AI 实验 Agent。

本次目标：实现真正由大模型驱动的开放式自然语言交互，消除固定回复和简单关键词匹配造成的伪智能体验。

严格遵守 AGENTS.md、产品总规划和页面交互规范，不修改这三份文档。

一、检查现有实现

检查 Agent 的意图识别、普通问答、工具选择、对话上下文和回复生成逻辑。

重点查找：

- 硬编码的用户问题与固定回答
- 通过关键词直接决定实验类型
- 普通问题被强制转换为实验
- 使用预设文本冒充模型回复
- 无法理解用户连续追问
- 对话上下文丢失

二、实现真正的自由对话

普通聊天、日常问题、写作、计算机知识问答等内容，应通过用户配置的真实大模型动态生成回答。

不要使用固定问答库作为主要回复方式。

保留正常的系统提示词、安全约束和必要的错误提示。

三、统一智能意图决策

不要求用户手动切换聊天或实验模式。

Agent 根据当前消息、对话历史、用户目标和可用工具自主判断：

- 直接回答
- 提出澄清问题
- 规划实验
- 调用实验工具
- 解释已有实验
- 修改或优化实验
- 说明当前能力限制

不要依靠简单关键词匹配决定用户意图。

四、实现上下文理解

支持连续多轮对话。

例如：

用户：帮我研究 CPU 调度。

AI：分析目标并规划实验。

用户：换成时间片轮转。

AI：理解是在修改刚才的实验。

用户：为什么等待时间变长了？

AI：读取当前实验真实指标并解释。

用户：那试试更大的时间片。

AI：提出新的合法配置并等待确认。

不能每次都把用户消息当成全新的独立问题。

五、保持 Agent 工具能力

保留现有自主规划、工具选择、参数校验、用户确认、实验运行、结果观察和多轮决策功能。

普通聊天不应无故调用实验工具。

实验任务仍然必须使用真实引擎，不能由模型编造计算结果。

六、异常与安全

AI API 不可用时显示真实错误，不允许返回伪造的正常回答。

没有外部工具时，不得声称已经完成外部操作。

保留 API Key 安全保护、工具白名单、执行次数限制和用户确认机制。

七、测试

测试日常聊天、开放式写作、计算机问答、模糊问题、连续追问、实验创建、实验修改、结果解释以及不支持的外部操作。

检查每种情况是否调用正确处理流程。

不得通过硬编码测试问题的答案来通过测试。

八、开发记录

保留真实 Prompt、代码修改、测试结果和 Bug 修复过程。

完成后说明哪些回复来自真实模型，哪些属于必要的系统提示或错误信息。

不要修改无关 UI，不要扩充课程内容。

本次只完善开放式智能交互和上下文能力。
```

## 修改前审计

单轮创造台已有真实模型调用。常规问答和实验配置都由模型返回，页面中的示例属于输入提示。未发现 Agent 依据用户消息关键词直接选择实验引擎。上一阶段的最终实验报告由程序读实测指标生成，有明确的数据来源。

主要缺口是多轮入口固定使用平台主模型，模型决策格式只支持实验、实验结案、澄清和不支持。工作台完成一轮后没有通用输入框，用户只能在专门的表单里答复某个澄清问题。旧单轮入口的短历史保存在组件中，跳转到方案页会清空对话。

## 实施

创造台默认页面和既有实验的提问入口使用统一输入框。对话按访客隔离并存入任务版本。模型收到当前消息、最近十轮消息、待确认方案、已有实验目标和授权的 Run 指标。刷新后可以读取整段已提交的对话。用户从既有实验回来提问时，该方案或实际 Run 可以作为起点。

普通内容直接显示选中模型返回的正文。写作保留换行。模型根据上下文选择澄清、直接回复、解释、实验提议或能力说明。解释引用真实轮次和指标，服务端会拒绝不存在的引用。只有实验提议能包含白名单工具调用。工具必须通过现有 Schema，并在用户明确确认后才能执行。回复服务失败时，保留消息并提供重试。用户改发新消息时，前一条未获回复的消息也会进入历史。

对话复用「AI 服务设置」当前选择。平台模型继续使用已有的价格和配额校验。自带 Key 使用原有临时凭证机制。工具执行保持原有 6 次实验决策、12 步和 4 轮上限。普通回复不占用实验步骤，每段对话最多提交 24 次模型请求。

### 回复来源

| 页面内容 | 来源 |
| --- | --- |
| 日常问答、写作、知识讲解、澄清、能力说明 | 当前选中模型生成，保存模型名称和原回复 |
| 实验方案说明、新参数建议和一般结果解释 | 模型生成，服务端校验方案、引用和权限 |
| CPU 调度结果解释 | 模型选择实测证据。程序列出所选指标的各进程变化和仿真口径 |
| 运行指标、证据行、最终报告的数值对比 | 真实引擎和已保存的 Run，由程序读取或计算 |
| 等待确认、稍后重试、额度与 Schema 错误 | 真实任务状态及模型服务错误，由系统显示 |

## 验证

- 浏览器在默认创造台提交日常问题。现有开发服务返回「今日免费额度已用完」。刷新后，消息、错误和重试入口还在，界面没有显示 AI 回复。
- 隔离的开发测试进程仍走同一个 Agent 接口、真实 SiliconFlow 免费模型和原有价格校验。日常建议、两句小诗、环形队列问答均得到 `answer`，没有提议工具。含糊指代得到 `clarify`。要求代发邮件得到 `unsupported`，模型说明只能协助起草。
- 真实实验对话在同一会话按用户确认运行 FCFS 与 RR。使用 P1（0，6）、P2（1，4）、P3（2，3）。平均等待为 4.33 与 6.00。解释引用对应轮次，接着把 RR 时间片从 2 提议为 4，保持原进程。新方案停在待确认。
- 最终版本用相同输入重新运行两轮，真实模型选择了第 1、2 轮的等待证据。程序从 Run 读出 P1 的等待 0 → 7、P2 的 5 → 5、P3 的 8 → 6，并明确切换不计时。这次解释复测使用隔离试验中预先准备并明确确认的配置，参数选择和修改的真模型证据见上一条。
- DeepSeek 自带 Key 路由通过测试响应验证了配置作用及密钥隔离。真实正向联调使用平台免费模型。
- `npm run typecheck`、139 项自动化测试和 `npm run build` 通过。三份保护文档的 SHA-256 与开发前相同。

## 发现与修复

1. 无回复的一条消息原本会被下一条覆盖。改为保存其正文和未回复状态，并作为后续模型上下文。
2. 模型曾把 FCFS 策略写成数组。Schema 拦截了该方案。明确策略字段是单个字符串，复测后生成了合法配置。
3. 模型多次把实测数值误写成证据轮次。服务端拒绝引用。开放对话改用程序列出的证据 ID，由模型挑选并校验。
4. 模型曾把进程切换次数解释为本模拟的时间开销。提示修正后仍有误述。CPU 解释改为模型选证据，程序从 Run 读取各进程等待、响应或周转，并展示实际仿真口径。
5. 模型第一次回答改写请求时重复了原诗。提示中明确要求新稿。另一次真实联调中首条创作请求遇到服务错误，保留该消息后，下一条成功沿用「黄伞」约束写出安静语气的两句诗。自动化测试另验证已回复的原文和修改要求会一并进入模型上下文。
6. 新测试起初共享测试进程的免费额度，整套运行时会提前触发总限额。拆开各测试的额度状态，保留应用本身的限制。
